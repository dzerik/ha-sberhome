# Design

## Context

База: опубликованная 6.4.0b6. В `intents/encoder.py` TIME decode сохраняет
только rrule, encode пишет execute_at=null и пропускает пустой rrule.
В `www/components/sberhome-intent-modal.js` parseRrule возвращает только
days/hour/minute; buildRrule всегда создаёт DAILY и новый DTSTART.
Подробные локальные воспроизведения и источники находятся в
[исследовании №61](../../../research/2026-11-04-issue-61-api-contracts.md).

## Decisions

1. Данные TIME и возможность редактирования разделяются. Неизвестная форма
   не становится пустым/упрощённым расписанием и не теряется при правке имени.
2. Простой редактор охватывает только доказанно представимые им формы.
   Для новых расписаний исходный кандидат — штатный DAILY, один час/минута,
   BYSECOND=0, непустое подмножество BYDAY, заданный TZID.
   Консервативный whitelist: один DTSTART с распознаваемым IANA TZID,
   один RRULE, только FREQ=DAILY, WKST=MO, BYDAY без ordinal, один BYHOUR
   0..23, один BYMINUTE 0..59 и BYSECOND=0; без COUNT/UNTIL/INTERVAL,
   дополнительных content lines и неизвестных значимых параметров.
   Это подмножество UI, не описание всех возможностей облака. При расхождении
   TZID и scenario.timezone форма остаётся read-only до явного разрешения
   неоднозначности; несвязанные правки сохраняют исходные данные.
3. Изменение часов/дней не заменяет DTSTART текущим временем и не меняет
   timezone. COUNT/UNTIL/INTERVAL, несколько времён, calendar и другие
   неизвестные параметры не отбрасываются ради доступности простого UI.
4. Пустые дни считаются незавершённым вводом, а не «каждый день».
   Пустое время и нераспознаваемая зона в простом редакторе также блокируют сохранение;
   не подставлять 00:00 или фиксированную дату. Не смешивать разные
   TZID и scenario.timezone без явного решения.
5. Cancel, active=false и DELETE сценария не подменяют удаление TIME.
   Сетевой контракт удаления фиксируется только после живой проверки.

## Experiment

Использовать только созданные в этом опыте cloud ID. Действия — исключительно
SCENARIO_SET_ACTIVE на отдельные временные сценарии-цели; никаких команд
устройствам, уведомлений, TTS или переключения настоящего домашнего режима.
После каждой mutation перечитывать состояние и сохранять очищенный результат.

Временные группы проверки: неизменённые контроли A/B; удалённый TIME + PHRASES;
перенос A → B; два TIME A/B с удалением A; последний TIME без PHRASES.
Проверить состояния целей после A и B. Отсутствие исполнения засчитывается
только при успешном положительном контроле соответствующего срока.
В каждом успешном PUT сохранять id, timezone, actions, PHRASES и активность.
Для последнего триггера зафиксировать принятие/отказ сервера и состояние
после ошибки; не предполагать семантику пустого OR заранее.

Созданные ID записываются до следующей mutation, cleanup выполняется даже
при ошибке; удаляются только собственные cloud ID и точные HA registry entries.
Финальная проверка: исходный набор сценариев и домашние переменные сохранены.

## Live Findings

Проверка A/B и cleanup завершены; подробные входы, результаты и границы
доказательств — в [validation.md](validation.md).

- Удаление TIME + PHRASES принято; запуск в A отсутствовал при успешном контроле.
- Перенос A → B убрал A и выполнился в B; остальные поля сохранены.
- Из двух TIME удаление A сохранило исполнение B.
- Пустой набор триггеров отклонён: HTTP 500/code 2, bad nested condition.
  GET и исполнение в A подтвердили сохранение прежнего TIME.
  Клиентская политика: блокировать удаление последнего триггера до запроса.
- Отдельный schedule endpoint и замена id не потребовались. Cancel и active=false
  не использовались для подмены удаления.
- Все 12 временных cloud объектов удалены; исходные 12 сценариев и режим
  дома сохранены, HA registry не содержит созданных ID.

## Open Questions

- Как официальный клиент представляет одноразовый execute_at? Это отдельная
  неопределённость; поведение на синтетическом JSON не подтверждает API.
- Какие сложные RRULE, EXDATE/RDATE и дополнительные time_data поля принимает
  облако? Первый UI их не редактирует, но сохраняет полученные формы целиком.

## Scope Boundary

Изменение реализовано, проверено на финальной сборке HA и выпущено
после CI как 6.4.0b7. Живые результаты фиксируются
в `validation.md`, гипотезы не превращаются в нормативный сетевой контракт.
