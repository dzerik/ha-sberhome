# Validation: сохранность и удаление расписаний

Дата: 2026-11-04. База: **6.4.0b6**. Этап — исследование, без реализации.
[Предварительный анализ](../../research/2026-11-04-issue-61-api-contracts.md).

## Метод и границы доказательств

Проверка выполнена через Home Assistant MCP, команды
`sberhome/intents/create`, `get`, `update`, `delete` и `list`.
Существующий IntentService преобразовывал spec в POST/PUT gateway;
путь обновления из исходников — `PUT /scenario/v2/scenario/{id}`,
с `id` в теле. Ответы и поведение ниже получены от живого облака через
этот путь, а не от MockTransport.

Это не прямой HTTP wire capture: сравнение GET выполнено на нормализованном
IntentSpec. Сохранность неизвестных time_data/metadata и различий missing/null
таким GET не доказывается. Контракты других endpoints №61 не исследовались.
[Источник маршрута](../../../custom_components/sberhome/intents/service.py#L98).

Созданы 6 сценариев-целей и 6 сценариев с расписаниями. Действия последних —
только SCENARIO_SET_ACTIVE на отдельную временную цель. До испытания все
цели выключены; их собственные действия выключали только самих себя и
не запускались вручную. Команд устройствам, уведомлений и TTS не было.
В PUT проверяемые сценарии оставались включёнными: active=false и Cancel
не использовались как подмена удаления TIME.

Штатные правила: общий DTSTART, Europe/Moscow, FREQ=DAILY, WKST=MO,
BYDAY=MO,TU,WE,TH,FR,SA,SU, один BYHOUR/BYMINUTE, BYSECOND=0.
Срок **A — 18:03:00 MSK**, **B — 18:05:00 MSK**.
Отдельные неизменённые контроли имели тот же дом, timezone и правило
соответствующего срока. До A все шесть целей имели enabled=false.

## Mutation → GET

| Изменение | Результат живого облака | Результат перечитки |
| --- | --- | --- |
| Удалить TIME, оставить PHRASES | Принято | TIME=0, сценарий включён |
| Заменить TIME A на B | Принято | TIME=1, точное правило B, сценарий включён |
| Из двух TIME A/B удалить A | Принято | TIME=1, точное правило B, сценарий включён |
| Удалить последний TIME при PHRASES=[] | **Отклонено: HTTP 500, code 2, bad nested condition** | Прежний TIME=1 и включённое состояние сохранены |

Для всех четырёх случаев сравнение до/после подтвердило неизменность
id, name, home_id, enabled, phrases, actions, timezone и image в IntentSpec.
Два TIME были приняты и прочитаны ещё до удаления первого.

## Исполнение с положительными контролями

Значение в таблице — enabled отдельной временной цели. true означает,
что действие сценария активировало цель, false — этого пока не произошло.
После A наблюдение снято через **32 с**,
перед B — за **25 с**, после B — через **47 с**.

| Сценарий | После A | Перед B | После B |
| --- | --- | --- | --- |
| Контроль A | true | true | true |
| Контроль B | false | false | true |
| Удалён TIME, PHRASES сохранены | false | false | false |
| TIME перенесён A → B | false | false | true |
| Из двух TIME A/B удалён A | false | false | true |
| Удаление единственного TIME отклонено | true | true | true |

Оба положительных контроля сработали. Удаление TIME убрало прежний запуск A,
перенос не оставил A и дал исполнение B. Удаление только первого TIME
сохранило исполнение второго в B. После отклонённого удаления последнего
TIME сохранились не только данные GET, но и фактическое исполнение в A.
Это наблюдения в указанных временных окнах одной проверки на текущем API;
они не устанавливают поведение всех разновидностей RRULE.

## Очищенные формы запросов

Во всех примерах ID и фразы заменены обозначениями; прочие неизменённые
поля сценария сохранены из GET. Это схема отправленного изменения через
IntentService, не полная копия HTTP-трафика.

- Удаление: triggers `[TIME(A)]` → `[]`, phrases `[TEST_PHRASE]` сохранены.
  Encoder собирает CONDITIONS/OR с единственным PHRASES.
- Перенос: triggers `[TIME(A)]` → `[TIME(B)]`, остальные поля сохранены.
- Два TIME: `[TIME(A), TIME(B)]` → `[TIME(B)]`, PHRASES сохранены.
- Последний: triggers `[TIME(A)]` → `[]`, phrases `[]` → `[]`.
  Encoder собирает CONDITIONS/OR с пустым conditions; gateway отклоняет его.

Отдельный endpoint удаления расписания, другое поле ID, изменение метода
или пути для этих операций не потребовались. Это не доказывает отсутствия
альтернативных endpoint у провайдера.

## Контракт следующей реализации

1. Сохранять весь TIME, включая opaque-формы, при несвязанной правке.
2. Простой UI — только для строго распознанного канонического DAILY;
   сохранять DTSTART/TZID, не превращать прочие правила в DAILY.
3. Пустые дни/время и нераспознаваемая зона блокируют сохранение.
4. Изменение/удаление — существующий PUT целого сценария; сохранять
   остальные условия, действия, ID и активность. Не добавлять Cancel/disable
   в качестве обхода удаления расписания.
5. Последний триггер без PHRASES блокировать в UI и backend до запроса,
   вместо предъявления пользователю серверного 500. При любой ошибке
   не показывать ложное подтверждение удаления.

Не установлено: официальный формат одноразового execute_at; поддержка
облаком всех сложных RRULE, EXDATE/RDATE и дополнительных полей.
Контракт сохранности полученного JSON не требует угадывать их семантику.
Создание/редактирование одноразовых расписаний остаётся отдельным scope.

На момент завершения исследования реализация ещё не начиналась. После
разрешения пользователя начата 6.4.0b7; результаты приведены ниже. До
проверки финальной сборки и выпуска change остаётся активным.
