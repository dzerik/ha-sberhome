# №61: анализ контрактов API и расписаний

Дата: 2026-11-04. Основание: [issue #61](https://github.com/dzerik/ha-sberhome/issues/61),
связанный scope — [#62](https://github.com/dzerik/ha-sberhome/issues/62).
Исследован код опубликованной **6.4.0b6**, commit
`9dfcd8f70b33942b565ea0946da7ec4eb2a5f608`.

## Решение по результатам анализа

Сейчас нет подтверждённого основания менять спорные URL, GET на POST или
`id` на `scenario_id`. Сначала нужны наблюдения конкретных запросов и ответов.
При этом локально воспроизведена потеря смысла сложных расписаний в редакторе.
Ближайшее изменение целесообразно ограничить сохранением TIME-условий и
проверкой удаления расписания; остальные пункты №61 исследовать отдельно.

В этой работе изменён только этот документ. Выполнены чтение исходников,
тестов, предыдущих отчётов, публичных ресурсов провайдера и локальные пробы
существующих функций Python/JavaScript. Новых запросов к авторизованному
облаку, изменений HA, реализации, релизов и комментариев GitHub не было.
Все 407 проверенных файлов исходников, тестов, версий и CHANGELOG совпадали
с v6.4.0b6 перед фиксацией отчёта. Прежний dirty checkout содержит уже
опубликованные изменения; этот diff не является результатом текущего анализа.

## Уровни доказательств

- **Локально воспроизведено** — фактический результат существующего кода
  на указанных входах; принятие этих входов облаком из него не следует.
- **Предыдущая живая проверка** — сохранённый результат работы с API;
  в текущем анализе повторно не выполнялась.
- **Реализация / мок** — намерение клиента и поведение синтетического сервера;
  не подтверждают реальный контракт облака.
- **Не установлено** — требуется запрос/ответ или первичный код провайдера.
  Отсутствие результата публичного поиска не доказывает отсутствие контракта.

## Расписания: что уже есть

Редактор TIME и генератор RRULE уже реализованы. Отдельного метода удаления
расписания в **нашем клиенте** нет: UI удаляет триггер из draft, encoder строит
новое дерево условий, IntentService отправляет PUT всего сценария.
Это не доказывает отсутствие отдельного endpoint у провайдера.
Источники: [UI remove](../../custom_components/sberhome/www/components/sberhome-intent-modal.js#L278),
[encoder](../../custom_components/sberhome/intents/encoder.py#L324),
[PUT](../../custom_components/sberhome/intents/service.py#L98),
[ScenarioAPI](../../custom_components/sberhome/aiosber/api/scenarios.py#L78).

Предыдущая живая проверка подтвердила исполнение штатного DAILY RRULE с
BYDAY всех дней и BYSECOND=0. Контрольный сценарий выполнился, отменённый
через Cancel — нет, при этом его автосрабатывание осталось включённым.
Это доказательство поведения **Cancel**, не удаления TIME через PUT.
[Отчёт 6.4.0b6](../changes/archive/2026-11-04-sync-home-mode-and-scenario-controls/validation.md#живой-ha-и-облако).

Нужно различать четыре операции:

1. Удалить TIME-условие — убрать правило будущих запусков, сохранив сценарий.
2. Cancel — пропустить ожидающий запуск, сохранив расписание и активность.
3. Выключить автосрабатывание — PATCH `active=false`.
4. Удалить сценарий — DELETE всего объекта.

Считать пункты 2–4 проверкой пункта 1 нельзя.

## Локально воспроизведённые проблемы TIME

Пробы выполнялись на существующих функциях без сетевых вызовов и изменений
репозитория. Для Python вызывались `decode_scenario` → `encode_scenario`.
Для JavaScript из исходника непосредственно исполнялись `parseRrule`,
`buildRrule`, `describeDays`; реализация этих функций в пробах не подменялась.
Временные материалы: `/tmp/ha-sberhome-issue61-{local-probe.py,js-probe.cjs}`,
результаты — `/tmp/ha-sberhome-issue61-{python,js}-probe.json`.
Существенные результаты приведены ниже, поэтому отчёт не зависит от хранения `/tmp`.

### 1. Сложный RRULE отображается упрощённо и меняется при правке времени

`parseRrule` извлекает только BYDAY, первое число BYHOUR и первое число
BYMINUTE. `buildRrule` всегда создаёт DAILY, новый DTSTART, BYSECOND=0.
Источник: [UI helpers](../../custom_components/sberhome/www/components/sberhome-intent-modal.js#L1795).
Редактор пересобирает правило при изменении дня или времени:
[setTime](../../custom_components/sberhome/www/components/sberhome-intent-modal.js#L1001).

| Синтетический вход RRULE | Результат текущих функций |
| --- | --- |
| `FREQ=MONTHLY;BYMONTHDAY=15;BYHOUR=9;BYMINUTE=0;COUNT=3` | Digest «каждый день в 09:00»; изменение минут создаёт бессрочный DAILY, без BYMONTHDAY и COUNT |
| `FREQ=WEEKLY;INTERVAL=2;BYDAY=MO;BYHOUR=9;BYMINUTE=0;UNTIL=20301231T210000Z` | Digest «Пн в 09:00»; изменение минут теряет INTERVAL=2 и UNTIL |
| `FREQ=DAILY;BYHOUR=9,18;BYMINUTE=0;BYSECOND=0` | Отображается только 09:00; после изменения остаётся одно время |

Это подтверждённое ограничение UI для таких строк. Само по себе оно не
доказывает, что Сбер создаёт или принимает все эти варианты. Без изменения
дней/времени исходный `rrule` проходит Python decode/encode как строка;
обычное открытие редактора не пересобирает его автоматически.

COUNT, UNTIL, INTERVAL и DTSTART имеют самостоятельный смысл в
[RFC 5545 §3.3.10](https://datatracker.ietf.org/doc/html/rfc5545#section-3.3.10).
Это источник семантики RRULE, не спецификация поддерживаемого Сбером подмножества.

### 2. TIME сохраняет только rrule

[Python decoder](../../custom_components/sberhome/intents/encoder.py#L192)
не переносит `execute_at` и прочие поля `time_data` в IntentTrigger.
[Encoder](../../custom_components/sberhome/intents/encoder.py#L347)
всегда пишет `execute_at: null` и отбрасывает TIME при пустом rrule.

Результаты локального round-trip:

| Вход time_data | Выход |
| --- | --- |
| `execute_at: null`, обычный DAILY rrule | Сохранён без потерь — положительный контроль |
| `execute_at: "2030-01-15T09:00:00+03:00"`, `rrule: ""` | TIME полностью исчезает |
| DAILY rrule и дополнительное неизвестное поле | rrule остаётся, дополнительное поле теряется |

Последние два случая синтетические. Поддержка облаком одноразового
`execute_at`, его точного формата и дополнительных полей **не установлена**.
Установлено, что текущий decoder не обеспечивает их сохранность.
UI также не позволяет сохранить time-триггер без непустого rrule:
[validation](../../custom_components/sberhome/www/components/sberhome-intent-modal.js#L323).

### 3. Пустой выбор дней становится всеми днями

`buildRrule([], 9, 0, tz)` выдаёт BYDAY всех семи дней, хотя
`describeDays([])` возвращает «никогда».
В текущем UI снятие последнего выбранного дня сразу пересобирает правило
с семью днями. Это локально установленное поведение, без неопределённости
REST. Требуется явно выбрать ожидаемый UX: запретить пустой выбор либо
объяснить его значение; не считать пустой список выключением расписания.
[Источники](../../custom_components/sberhome/www/components/sberhome-intent-modal.js#L1795).

## Что на самом деле проверяют тесты

- [TIME tests](../../tests/intents/test_triggers.py#L149) закрепляют
  `execute_at: null` и отбрасывание пустого rrule. Потери execute_at,
  метаданных и смысловой round-trip сложных правил ими не проверяются.
- [Device.move tests](../../tests/aiosber/api/test_devices.py#L258)
  проверяют JSON, включая `parent_id: null`, но не URL и HTTP-метод.
- [Group mutation tests](../../tests/aiosber/api/test_groups.py#L169)
  проверяют body, но не URL/метод.
- [Template tests](../../tests/aiosber/api/test_scenario_templates.py#L31)
  проверяют suffix URL, но не HTTP-метод. MockTransport отвечает синтетически.

Таким образом, зелёные тесты и высокий процент покрытия не закрывают
wire-вопросы issue. Будущие регрессии стоит привязывать к очищенным реальным
запросам и проверять метод, путь, параметры, тело, ответ и последующую перечитку.

## Уточнения остальных контрактов

### Device и Group

Текущие запросы:

| Операция | Запрос и JSON |
| --- | --- |
| Device.move | PUT `/devices/{id}/parent`, `{"parent_id": value}` |
| Group.rename | PUT `/device_groups/{id}/name`, `{"name": value}` |
| Group.move | PUT `/device_groups/{id}/parent`, `{"parent_id": value}` |
| Group.set_image | PUT `/device_groups/{id}/image`, `{"image_id": value}` |

Источники: [devices.py](../../custom_components/sberhome/aiosber/api/devices.py#L133),
[groups.py](../../custom_components/sberhome/aiosber/api/groups.py#L150).
Альтернативы из issue не подтверждены и не опровергнуты.
Переименование группы уже используется для комнат в панели:
[rename_room](../../custom_components/sberhome/websocket_api/rooms.py#L125).
Поэтому проверка rename имеет непосредственную пользовательскую ценность.
Device.move в отдельный безопасный опыт без подходящего тестового устройства
включать не следует: перенос настоящего устройства изменит рабочую структуру дома.

### Templates

Все методы вызывают GET: `/scenario-templates/short`, `/device`, `/group`,
`/rooms`, `/screen/`, `/hide`; фильтров и JSON-body нет.
[Источник](../../custom_components/sberhome/aiosber/api/scenario_templates.py#L31).
Подтверждать метод и ответ нужно для каждого пути. Ошибка одного endpoint
не доказывает, что все шесть требуют POST.
Неожиданный успешный JSON сейчас превращается в пустой список через
`_ensure_list`: один пустой результат нельзя считать доказательством
отсутствия шаблонов, не проверив исходную форму ответа.

### id и scenario_id

`ScenarioBody` — историческое название из issue, такого класса в текущем
коде нет. ScenarioAPI принимает dict. В пути панели POST удаляет `id`,
PUT добавляет `body["id"] = scenario_id`, GET ожидает `id`.
[Источник](../../custom_components/sberhome/intents/service.py#L71).
Успешный предыдущий живой CRUD
[CONDITIONS](../changes/archive/2026-11-04-edit-nested-scenario-conditions/validation.md)
подтверждает принятие этой дорожки с id. Он не устанавливает обязательность
поля или наличие alias. Вложенные `scenario_id` в set-requires и
SCENARIO_SET_ACTIVE/CHECK_SCENARIO — другие контракты, оснований массово
переименовывать их или верхнеуровневое поле нет.

### WS: не смешивать три имени

1. Входящий JSON содержит поле `group_state`:
   [DTO](../../custom_components/sberhome/aiosber/dto/ws.py#L38).
2. Внутренний Topic.GROUP_STATE имеет строковое value `group_state`:
   [enum](../../custom_components/sberhome/aiosber/dto/enums.py#L373).
3. В query подписки передаётся uppercase `GROUP_STATE`:
   [coordinator](../../custom_components/sberhome/coordinator.py#L1728),
   [transport](../../custom_components/sberhome/aiosber/transport/ws.py#L328).

Наличие ключа JSON не определяет регистр query-параметра. Успешный handshake
с несколькими topics тоже не доказывает доставку событий каждого типа.
Нужен настоящий frame от изменения тестовой группы при зафиксированной
подписке. Подменять uppercase на lowercase без этого оснований нет.

## Следующий этап — предложение, без реализации

Первое узкое OpenSpec-изменение: **сохранность TIME и удаление расписания**.

1. Зафиксировать поддерживаемое редактором подмножество RRULE. Неизвестные
   формы сохранять полностью; до подтверждения контракта предлагать для них
   чтение без преобразования в простой DAILY. Не расширять поддержку на весь RFC
   только на основании синтетических примеров.
2. Снять форму одноразового TIME в официальном клиенте, если он её поддерживает;
   проверить execute_at, timezone и дополнительные поля. Определить поведение
   пустого выбора дней и последнего удалённого триггера.
3. Проверить на временном сценарии TIME + PHRASES: удалить только TIME через PUT,
   сделать GET, убедиться в сохранении PHRASES, tasks, timezone, ID и активности.
4. Проверить отсутствие старого отложенного запуска в его прежний срок.
   Параллельный неизменённый контроль должен выполниться. Действия обоих
   сценариев могут менять только активность отдельных временных сценариев-целей,
   как в проверке 6.4.0b6. Отключение проверяемого сценария не заменяет удаления
   TIME: оно сделало бы опыт неразличимым с обычным выключением автосрабатывания.
5. Отдельно проверить смену времени A → B: нет выполнения в A, есть в B;
   удаление одного из двух TIME; допустимость удаления последнего триггера.
   Не угадывать семантику пустого CONDITIONS/OR.
6. Только после результатов формулировать нормативный delta-spec, изменения
   и регрессионные тесты. Удалить все созданные cloud/HA объекты после опытов.

Второй этап №61: подтверждение templates чтением, затем rename/move/image
на временной пустой группе и наблюдение WS. Device.move отложить до появления
подходящего тестового устройства. Все wire-наблюдения сохранять очищенными:
метод, route-шаблон, body, статус, ответ и GET после операции; без токенов,
настоящих идентификаторов дома/устройств и персональных названий.

Новая бета и деплой на этом этапе анализа не требуются. Issue №61 пока
нельзя закрыть: точные спорные контракты ещё не подтверждены в облаке.
