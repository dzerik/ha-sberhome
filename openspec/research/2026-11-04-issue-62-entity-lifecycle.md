# №62: жизненный цикл сущностей сценариев, домов и групп

Дата: 2026-11-04. База: 6.4.0b7, main
`57c713f5d9553cf7a891bd038403f61330fdcb0b`.
[Issue #62](https://github.com/dzerik/ha-sberhome/issues/62).

## Результат

Оставшийся полезный scope — согласовать lifecycle уже существующих
automation entities. Новые endpoints и исследование устройств для этого
не нужны. Приоритетный дефект: общий HA-device «Sber Groups» удаляется
автоматической чисткой после трёх успешных полных обновлений даже тогда,
когда группа и её участники остаются в выдаче.

Это анализ, без реализации. Код, тесты репозитория, версии и HA не менялись;
коммит, деплой, релиз и комментарии GitHub не выполнялись. Исследовательские
пробы находятся в /tmp и работают на настоящем тестовом Home Assistant
с FakeSberCloud/httpx.MockTransport. Запросов к настоящему облаку и железу нет.

## Уже сделано в №62

- Переключатели at_home и активности сценария существуют.
- Кнопки запуска, stop/cancel существуют; новые сценарии динамически получают
  три кнопки, удалённые становятся unavailable.
- WS домашней переменной вызывает авторитетную перечитку API.
- Сохранность и редактирование поддерживаемых TIME выпущены в 6.4.0b7.

Это не означает полной динамической поддержки перечисленных сущностей:
switch и button сейчас по-разному обрабатывают изменения инвентаря.

## Подтверждённые дефекты

### 1. Автоматическая чистка удаляет действующие группы

`SberGroupSwitch.device_info` использует общий identifier `(DOMAIN, "groups")`:
[switch_groups.py](../../custom_components/sberhome/switch_groups.py#L49).
В `_collect_identifiers` защищены `group:{id}`, `indicator` и `scenarios`,
но **не `groups`**:
[registry_maintenance.py](../../custom_components/sberhome/registry_maintenance.py#L101).
После трёх промахов `prune_stale_devices` удаляет device registry entry,
что каскадно убирает сущности:
[prune](../../custom_components/sberhome/registry_maintenance.py#L36).

Контроль без изменения FakeCloud между опросами:

| Полный refresh после setup | GROUP есть в cache | HA registry entity | HA state |
| --- | --- | --- | --- |
| 1 | да | есть | есть |
| 2 | да | есть | есть |
| 3 | да | отсутствует | отсутствует |
| 4 | да | отсутствует | отсутствует |

Это не реакция на удаление группы в облаке. Ошибка именно в сопоставлении
service identifier с набором live identifiers. Простое добавление discovery
без исправления maintenance недостаточно: known-set может считать уже
удалённую HA-сущность зарегистрированной и не восстановить её.

### 2. Новые переключатели сценариев и группы не обнаруживаются

[switch.async_setup_entry](../../custom_components/sberhome/switch.py#L31)
перечисляет дома, сценарии и непустые GROUP один раз. Listener для новых
объектов отсутствует. У кнопок он уже есть:
[button.async_setup_entry](../../custom_components/sberhome/button.py#L41).

В тестовом HA после добавления сценария и `async_refresh_scenarios`:

| Новая сущность | Результат |
| --- | --- |
| run | появилась |
| stop | появилась |
| cancel | появилась |
| active switch | **не появилась** |

Новая непустая GROUP после успешного полного refresh тоже не получила switch.
Случай «пустая группа появилась при setup, затем получила первого участника»
следует из того же setup-only пути; отдельной пробой пока не воспроизводился.

### 3. Переименование не отражается в HA

Имена run/active, translation placeholders stop/cancel и имя группы
фиксируются конструкторами. Чтение текущего состояния их не обновляет.
Источники: [scenario buttons](../../custom_components/sberhome/button.py#L141),
[active switch](../../custom_components/sberhome/switch.py#L147),
[group](../../custom_components/sberhome/switch_groups.py#L38).

В пробе сценарий переименован «Первый» → «Переименован»: после перечитки
все четыре существующих сущности остались с «Первый» в friendly_name.
При исчезновении и возврате того же ID под именем «Вернулся» прежние entity_id
восстановились, но старое имя тоже осталось. Для группы rename воспроизведён
до того, как maintenance успел удалить её: имя также не изменилось.

Обновлять следует исходное имя/placeholder, сохраняя пользовательские
переименования, entity_id и все существующие unique_id. Одной замены
значения placeholder недостаточно считать исправление доказанным:
проверка должна пройти через фактический registry/friendly_name и кэш имени HA.

### 4. Список домов навсегда остаётся первым непустым снимком

[`_ensure_homes`](../../custom_components/sberhome/coordinator.py#L1025)
сразу возвращает управление, если self.homes непуст. Этот список используется
для чтения at_home и исходного создания переключателей.

В пробе после rename первого дома и добавления второго успешный полный
refresh обновил StateCache до двух домов с актуальными именами. Затем
`async_refresh_scenarios` всё ещё использовал старый self.homes:
второй дом отсутствовал и в at_home, и среди HA-переключателей.
Одного discovery listener в switch.py для этого недостаточно — нужен
актуальный авторитетный инвентарь домов.

### 5. Push исключённого из HA выбора участника не публикует состояние группы

[`_on_ws_device_state`](../../custom_components/sberhome/coordinator.py#L1919)
патчит StateCache для известного устройства независимо от выбора, но
уведомляет слушателей только для выбранного устройства. При этом
SberGroupSwitch агрегирует весь состав группы Сбера, включая невыбранные
для отдельных HA-сущностей устройства.

Проба: одно выбранное стороннее устройство и невыбранный участник GROUP.

| Шаг | reported on_off участника в cache | HA state группы |
| --- | --- | --- |
| Исходно | false | off |
| DEVICE_STATE с true от невыбранного участника | true | **off** |
| Дополнительное `async_update_listeners()` | true | on |

Это воспроизводит отсутствие уведомления; новый протокол WS не предполагается.
Исправление не должно создавать отдельные HA-сущности невыбранных устройств
или менять смысл bulk-команды группы.

### 6. Наличие группы не входит в availability

[`available`](../../custom_components/sberhome/switch_groups.py#L65)
проверяет успешность координатора и online участников из reverse index,
но не существование самой GROUP. В пробе группа удалена из списка groups,
а устройство временно сохраняет её ID в group_ids: switch остаётся `off`,
то есть доступным, хотя самой группы в авторитетном снимке уже нет.

После удаления membership дальнейший полный refresh каскадно убрал сущность
из-за дефекта maintenance, поэтому результат pure entity.available нельзя
выдавать за полный интеграционный lifecycle. Проверять нужно оба слоя.

## Что уже работает и должно сохраниться

- Удалённый сценарий переводит все четыре существующие сущности в unavailable.
  При возврате того же ID они используют прежние entity_id; active корректно
  меняет состояние. Кнопки с состоянием unknown до первого нажатия не являются
  ошибкой: это не переключатели.
- ID уже основаны на cloud ID. Смена имени не требует нового unique_id.
- В группе агрегируется reported on_off, а не локальный desired.
- У группы одна bulk-команда через существующий GroupAPI.set_state.
  Optimistic patch пишет desired участников, поэтому текущий тест desired
  не доказывает немедленного изменения reported/состояния группы.

Переработку optimistic semantics, состава команды во время await и новых
типов групп предлагается вынести из lifecycle scope.

## Предлагаемый объём следующего OpenSpec

Рабочее имя: `sync-automation-entity-lifecycle`.

1. Защитить реальный service identifier `groups` от ошибочного prune.
2. Добавлять новые home/active/group switch после успешного обновления;
   первоначально пустая GROUP появляется после наполнения. Повторное
   уведомление не создаёт дублей. Listener снимается при unload.
3. Обновлять исходные имена всех связанных сущностей, сохраняя overrides,
   entity_id, unique_id, disabled_by и пользовательские настройки registry.
4. Для исчезнувших объектов сохранять запись и показывать unavailable;
   возврат того же ID восстанавливает её. Общий service device не удаляется
   при изменении отдельных групп. GROUP → ROOM перестаёт быть bulk-switch.
5. Согласовать self.homes с успешным актуальным инвентарём. Ошибка/неполная
   выдача не считается подтверждённым удалением. Не добавлять лишний API-запрос
   на каждый state push, если достаточно уже обновлённого StateCache.
6. Уведомлять групповые сущности при изменении фактического состояния любого
   участника, сохраняя фильтрацию отдельных устройств и таймер полного polling.

Правила HA рекомендуют динамическое добавление через listener координатора
с очисткой при unload:
[dynamic-devices](https://contributors.home-assistant.io/core/quality-scale/dynamic-devices/).
Стабильные unique_id обеспечивают сохранение пользовательских настроек:
[entity registry](https://contributors.home-assistant.io/core/entities/registry/).
Эти рекомендации поддерживают направление исправления; конкретные дефекты
выше воспроизведены на установленном HA 2026.10.4.

## Проверки будущего изменения

| Сценарий | Ожидаемый результат |
| --- | --- |
| Неизменная GROUP, не менее четырёх полных refresh | Service device, registry entity и HA state остаются |
| Новый сценарий после setup | Один active switch и три кнопки, без reload и дублей |
| Новый дом / rename дома | Актуальные at_home и switch, прежние ID сохраняются |
| Новая или первоначально пустая GROUP получает участника | Появляется ровно один switch |
| Rename сценария/группы | Исходное имя обновляется; custom name/ID/disabled_by сохранены |
| Удаление/опустошение/смена type группы, orphan membership | unavailable, отсутствие команд на несуществующую GROUP, registry сохранён |
| Возврат ID / другой ID с прежним именем | Прежний ID восстанавливается; другой создаёт отдельную сущность |
| Push выбранного/невыбранного участника | HA state группы обновляется без раскрытия исключённых device entities |
| Сбой/degraded inventory → восстановление | Нет разрушительного удаления записей или потери настроек |
| Unload/reload | Нет оставшихся listeners, старые registry IDs используются повторно |
| Все пять локалей | Переводы управления сохраняются после rename |

## Воспроизводимость и состояние работы

Временный probe: `/tmp/test_ha_sberhome_issue62_probe.py`.
Результат: `/tmp/ha-sberhome-issue62-lifecycle-result.json`.
Команда:

```bash
PYTHONPATH=. .venv/bin/pytest -c pyproject.toml --no-cov \
  -p homeassistant -p tests.conftest /tmp/test_ha_sberhome_issue62_probe.py
```

Итог — **5 passed**, 0.56 с. Это исследовательские проверки текущего
поведения, а не регрессии уже исправленного кода. Первоначальная проба
предполагала unavailable после полного удаления группы и выявила фактическое
исчезновение state; отдельный контроль неизменённой группы установил причину.

Serena использована для символов и проверки доступной памяти (памятей не было).
Context7 запрошен для HA docs; точные рекомендации дополнительно сверены с
официальными страницами. Sequential-thinking отсутствует в наборе tools;
использован разрешённый AGENTS fallback — планирование средствами Codex.

Приоритет: сначала prune + согласованный lifecycle сценариев/групп,
затем включить актуализацию домов в тот же проверяемый контракт либо
выделить отдельной задачей. Достаточно локальных HA/FakeCloud-проверок;
выпуск и проверки настоящего API на этом этапе не требуются.
